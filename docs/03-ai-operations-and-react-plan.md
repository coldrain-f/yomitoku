# AI 생성 운영 및 React 전환 계획

## 1. AI 문항 생성 흐름

생성은 관리자만 시작할 수 있다. 비용이 발생하는 생성 API는 역할 검사를 통과한 요청만 처리한다.

```text
생성 조건 입력
  -> 생성 작업 생성(queued)
  -> 생성 모델 호출(generating)
  -> 규칙 검증(validating)
  -> 정답 검증과 품질 검증을 병렬 실행(validating)
  -> 판정
     -> 보완 요청 후 재생성(revising, 최대 2회)
     -> 검토 중 문항 생성(ready_for_review)
     -> 보류 문항 생성(held)
     -> 작업 실패(failed)
  -> 관리자 미리보기
  -> 보류 또는 게시 또는 삭제
```

### 1.1 LangGraph 오케스트레이션

v1 백엔드는 생성·검증 흐름을 처음부터 LangGraph로 구현한다. 이 흐름은 자유롭게 도구를 선택하는 에이전트가 아니라, 노드와 전이가 코드로 고정된 워크플로다.

- 그래프 노드는 `generate`, `validateSchema`, `verifyAnswer`, `verifyQuality`, `decide`, `revise`로 분리한다.
- `verifyAnswer`와 `verifyQuality`는 서로 독립적으로 실행하고 결과를 합쳐 판정한다.
- 각 노드의 입력과 출력은 JSON 직렬화 가능한 값만 사용한다. 모델 호출, 시간, 난수 등 비결정적 작업은 재시도 가능한 노드 안에서 실행한다.
- 체크포인트는 메모리가 아닌 영속 저장소에 저장하며, `generation_jobs.id`를 그래프 thread ID로 사용한다.
- 생성 요청 API는 작업 ID를 즉시 반환하고, 워커가 그래프를 비동기로 실행한다. 프론트는 폴링 또는 서버 전송 이벤트로 상태를 갱신한다.
- 그래프는 `ready_for_review`, `held`, `failed`에서 종료한다. 관리자의 게시·보류·삭제는 장기 실행 중인 그래프를 재개하지 않고, 문항 상태를 변경하는 일반 관리자 작업으로 처리한다.

기본 생성 모델은 설정값으로 관리하는 Claude Fable 5(`claude-fable-5`)다. 실제 사용한 생성·검증 모델 ID와 프롬프트 버전은 모든 작업에 함께 기록한다. 검증 모델은 생성 모델과 다른 모델 또는 다른 제공자를 우선 검토한다.

### 1.2 생성 입력

- 난이도: N5~N1
- 유형: 단문, 중문, 장문
- 주제: 추천(랜덤)을 포함한 선택 목록
- 후리가나: 현재 항상 `미표기`

생성 요청은 중복 클릭을 막고 `202 Accepted`와 작업 ID를 즉시 반환한다. 화면은 작업 상태를 폴링하거나 서버 전송 이벤트로 갱신한다.

### 1.3 생성 결과 형식

모델이 반환해야 하는 최소 구조는 다음과 같다.

```json
{
  "title": "地域の図書館が残すもの",
  "passage": "...",
  "question": "...",
  "choices": [
    { "text": "...", "isCorrect": false, "wrongExplanation": "..." },
    { "text": "...", "isCorrect": true },
    { "text": "...", "isCorrect": false, "wrongExplanation": "..." },
    { "text": "...", "isCorrect": false, "wrongExplanation": "..." }
  ],
  "explanation": "..."
}
```

- 모델 응답은 JSON Schema로 파싱한다. 문자열 치환이나 정규식만으로 JSON을 해석하지 않는다.
- 생성 직후 문항은 반드시 `review` 상태다. 생성 자체가 게시를 의미하지 않는다.

## 2. 생성 검증

### 2.1 필수 규칙 검증

다음 조건은 규칙 기반으로 우선 검사한다.

- 제목, 지문, 질문, 해설이 비어 있지 않다.
- 선택지는 정확히 4개다.
- 정답은 정확히 1개다.
- 선택지 텍스트가 중복되지 않는다.
- 해설이 정답 선택지와 지문 근거를 설명한다.
- 유형별 권장 시간과 지문 길이가 과도하게 어긋나지 않는다.
- 후리가나 표기 데이터는 생성하지 않는다.

### 2.2 의미 검증

규칙 검증 뒤 두 역할의 구조화된 AI 검증을 병렬로 실행한다. 같은 모델 계열만 사용하는 경우에도 생성 응답과 독립된 프롬프트·호출이어야 하며, 가능하면 다른 모델 또는 제공자를 검증자로 사용한다.

- 정답 검증자는 생성 모델이 제시한 정답을 먼저 보지 않고 지문, 질문, 선택지만 읽어 독립적으로 정답과 근거를 도출한다.
- 품질 검증자는 정답·해설까지 검토해 선택지의 모호성, 오답의 구분성, 해설의 논리를 평가한다.
- 각 검증 결과는 `passed`, `warning`, `failed`, 점수, `issueCodes`, 지문 근거를 JSON Schema로 반환한다.

- 정답이 지문으로 충분히 뒷받침되는가
- 오답이 정답과 구분되는가
- 해설이 정답의 근거와 일치하는가
- 요청 난이도와 유형, 주제에 대체로 맞는가

검증 결과는 `passed`, `warning`, `failed` 중 하나로 저장한다.

- 두 검증이 모두 `passed`: `review` 문항을 만들고 관리자 검토 후 게시 가능
- `warning` 또는 검증 결과 불일치: 보완 프롬프트와 함께 최대 2회 재생성한다. 재생성 뒤에도 해결되지 않으면 `held` 문항으로 저장한다.
- `failed`: 자동 게시 불가. 생성 결과를 보관할 수 있으면 `held` 문항으로 저장하고, 구조화된 결과를 만들지 못했으면 작업만 `failed`로 기록한다.

관리자 편집 화면에는 정답 검증, 오답 설계, 해설 논리와 전체 상태를 표시한다.

## 3. 비용과 운영 안전장치

- 생성 요청마다 사용자 ID, 입력값, 생성·검증 모델 ID, 프롬프트 버전, 입력/출력 토큰, 예상 비용, 실제 비용, 결과 상태를 저장한다.
- 관리자 계정 단위로 시간당/일당 생성 한도를 둔다. 한도는 서버 설정으로 관리한다.
- 같은 조건의 연속 요청에는 짧은 쿨다운을 둔다.
- API는 idempotency key를 받아 네트워크 재시도로 같은 생성 작업이 중복 생성되지 않게 한다.
- 모델 오류, 시간 초과, JSON 파싱 실패는 노드별 오류 코드와 함께 저장한다. 일시적 오류는 제한된 횟수로 재시도하고, 한도를 넘기면 `failed`로 종료한다.
- 프롬프트와 생성 결과에는 개인정보를 넣지 않는다.

### 3.1 생성 작업 상태

- `queued`: 생성 작업이 생성돼 워커를 기다리는 상태
- `generating`: 생성 모델 호출 중인 상태
- `validating`: 규칙 또는 AI 검증 중인 상태
- `revising`: 검증 피드백으로 재생성 중인 상태
- `ready_for_review`: 검토 중 문항이 생성돼 관리자 확인을 기다리는 종료 상태
- `held`: 보류 문항이 생성돼 관리자 검토를 기다리는 종료 상태
- `failed`: 문항을 만들 수 없었거나 재시도 한도를 초과한 종료 상태

## 4. 상태 운영 원칙

- `review`: 생성 또는 보류 취소 뒤의 내부 검토 상태다. 학습자에게 공개하지 않는다.
- `held`: 삭제하지 않고 보관하는 상태다. 게시 버튼은 미리보기에서 비활성화한다.
- `published`: 학습자가 목록에서 보고 풀 수 있는 상태다.
- `deleted`: 화면상 상태가 아니라 영구 삭제 완료 결과다. 복구하거나 보류로 바꾸지 않는다.

`generation_jobs`의 작업 상태와 `reading_items`의 문항 상태는 구분한다. 예를 들어 작업이 `ready_for_review`로 끝나면 문항 상태는 `review`이고, 작업이 `held`로 끝나면 문항 상태도 `held`다.

게시 문항을 보류로 바꾸면 새 학습 시작은 즉시 막는다. 기존에 이미 상세를 연 사용자의 제출은 정책상 허용하되, 제출 시 문항 상태를 다시 확인해 `held`이면 결과 저장 없이 목록으로 안내하는 방식을 권장한다.

## 5. React 전환 작업

문서와 API 계약이 안정된 다음 단계는 현재 `index.html`, `styles.css`, `app.js`를 React로 전환하는 작업이다. 이 전환은 디자인을 새로 만드는 작업이 아니라, 현재 화면과 동작을 유지하면서 실제 API 상태로 바꾸는 작업이다.

### 5.0 현재 상태

이 저장소에 React 1차 전환을 완료했다. 기존 정적 파일은 디자인 기준 시안으로 남겨 두었고, React 앱은 동일한 CSS와 클래스 구조를 사용한다. 현재 데이터와 로그인은 브라우저 메모리 목업이며, 다음 구현 단계에서 이 문서의 API 계약으로 교체한다.

2026-08-30 기준으로 공통 UI, 학습, 통계, 관리자 화면을 기능 폴더로 분리했고, `react-router-dom`으로 화면 전환을 URL 기반으로 바꿨다. 이후 전체 `src`를 TypeScript strict 모드로 전환해 문항, 시도, 필터, 생성 조건, 다이얼로그의 도메인 타입을 `src/types.ts`에 모았다. `App.tsx`는 목업 상태, 라우트 가드, 기능 조립을 담당하고, 표시·정렬·집계용 순수 함수는 `src/lib/reading.ts`에 둔다. 목록의 검색과 필터는 URL 쿼리(`q`, `level`, `length`, `status`, `sort`)에 남긴다. 백엔드 연결 때는 이 기능 경계를 유지한 채 각 기능의 목업 상태를 API 서버 상태로 교체한다.

현재 목업 라우트는 다음과 같다.

- `/`: 공개 독해 목록
- `/readings/:itemId`, `/results/:itemId`, `/statistics`: 로그인 필요 화면
- `/admin/readings`, `/admin/readings/new`, `/admin/readings/:itemId/edit`, `/admin/readings/:itemId/preview`: 관리자 전용 화면

문항과 시도 결과가 아직 브라우저 메모리에만 있으므로 풀이·결과 URL을 새로고침하거나 직접 열면 목록으로 되돌린다. 실제 API 연결 뒤에는 URL 매개변수로 문항과 결과를 다시 조회해 유지한다.

### 5.1 권장 기술 기준

- React + TypeScript (현재 적용 완료)
- Vite 또는 현재 선택한 React 빌드 도구
- React Router
- 서버 상태 관리: TanStack Query 또는 동등한 캐시/뮤테이션 도구
- 폼: React Hook Form과 스키마 검증 도구 또는 동등한 방식
- 아이콘: 현재와 동일하게 Lucide React

특정 라이브러리는 프로젝트를 시작할 때 한 번 확정하고, 화면마다 다른 상태 관리 패턴을 섞지 않는다.

### 5.2 권장 폴더 구조

```text
src/
  app/                 # 라우터, 전역 Provider, 레이아웃
  components/ui/       # Dialog, Button, Badge, Select, Pagination
  features/auth/       # 현재 사용자, 로그인, 로그아웃, 권한 가드
  features/readings/   # 목록, 필터, 풀이, 결과, 피드백, 오류 제보
  features/statistics/ # 학습 통계와 차트
  features/admin/      # 관리 목록, 편집, 생성, 미리보기, 검증
  lib/api/             # API 클라이언트와 타입
  styles/              # 토큰과 전역 스타일
```

### 5.3 화면 단위 전환

| 순서 | React 화면/기능 | 기존 기준 |
| --- | --- | --- |
| 1 | 공통 레이아웃, 헤더, Breadcrumb, Dialog | 공통 HTML과 CSS |
| 2 | 공개 목록, 검색, 필터, 정렬, 페이지네이션 | 목록 화면 |
| 3 | 인증 상태와 권한 가드 | 로그인/로그아웃 UI |
| 4 | 풀이, 타이머, 선택지 셔플, 제출 결과 | 풀이/결과 화면 |
| 5 | 학습 통계 | 통계 화면 |
| 6 | 관리자 목록과 편집 | 문항 관리/편집 |
| 7 | 생성, 작업 상태, 검증, 미리보기 | 생성/미리보기 |

### 5.4 상태 분리

- 서버 상태: 사용자, 목록, 문항 상세, 시도, 통계, 피드백, 관리자 문항, 생성 작업. API 캐시로 관리한다.
- 화면 상태: 열린 다이얼로그, 현재 선택지, 타이머 표시, 필터 다이얼로그의 임시값, 토스트. 컴포넌트 상태 또는 가벼운 전역 상태로 관리한다.
- 정답 여부는 제출 응답을 받기 전까지 클라이언트 상태에 두지 않는다.
- 선택지 순서는 화면 상태로만 보관하고, 제출에는 선택지 ID를 보낸다.

### 5.5 React 전환 완료 기준

- 현재 정적 HTML에 있는 모든 화면과 다이얼로그가 동일한 정보 구조와 상태 전환을 가진다.
- URL 직접 접근 시 역할에 맞지 않는 화면은 접근할 수 없다.
- 새로고침 뒤에도 서버에 저장된 목록, 시도, 통계, 관리자 상태가 유지된다.
- API 로딩, 빈 상태, 권한 없음, 네트워크 오류 상태를 제공한다.
- [04-acceptance-checklist.md](./04-acceptance-checklist.md)의 항목을 실제 브라우저 테스트로 통과한다.
