# 読み解く 포트폴리오 사례 연구

> AI-assisted full-stack product development · 최종 검증 기준일: 2026-09-20

## 한눈에 보기

| 항목 | 내용 |
| --- | --- |
| 제품 | 일본어·한국어 독해 학습과 콘텐츠 운영을 연결하는 웹 서비스 |
| 사용자 | 독해를 반복 학습하는 학습자, 문항을 생성·검토·게시하는 관리자 |
| 핵심 문제 | 문항 탐색, 장문 풀이, 결과 복습, 다음 학습과 콘텐츠 품질 관리가 분리되는 문제 |
| 기술 | React·TypeScript·Vite, FastAPI, PostgreSQL, Alembic, Docker Compose, LangGraph |
| AI 활용 | 구현 초안·반복 작업·테스트·문서화를 AI 에이전트와 협업하고, 요구사항·수용 기준·리뷰·최종 판단을 프로젝트 소유자가 맡는 방식 |

## 제품 흐름

```text
학습자
  로그인 → 조건으로 문항 탐색 → 풀이 시도 → 문항별 피드백 → 다음 미풀이/복습

관리자
  수동 등록 또는 AI 생성 작업 → 스키마·정답·품질 검증 → 검토 → 게시
```

AI 생성 결과는 검증을 통과해도 자동 게시하지 않는다. 비용이 드는 생성은 별도 작업으로 실행하고, 실패·재시도·사용량·검증 근거를 남긴다.

## 시스템 구조

```text
Browser (React / GitHub Pages)
  ├─ sessionStorage: 로그인 토큰, 현재 풀이 시도 식별자와 선택 답안
  └─ HTTPS Bearer API
       └─ FastAPI
            ├─ PostgreSQL: 문항, 시도, 응답, 학습 기록, 생성 작업
            └─ Worker (LangGraph): 생성 → 스키마 검증 → 정답/품질 검증 → 검토 대기
                 └─ Stub provider 또는 Anthropic provider
```

권한은 클라이언트 UI가 아니라 서버 토큰과 관리자 allowlist에서 결정한다. API 키와 JWT 비밀값은 프런트엔드에 두지 않는다.

## 문제를 구현으로 바꾼 사례

### 1. 빠른 검색에서도 최신 결과만 보이게 하기

검색어가 바뀔 때마다 요청하면 불필요한 네트워크 비용이 발생하고, 오래 걸린 이전 응답이 최신 결과를 덮을 수 있다. 목록·관리자 검색에 300ms 디바운스를 적용하고, 새 요청이 시작되면 이전 `AbortController` 요청을 취소했다. 일반 API 요청에는 15초 제한 시간을 뒀다.

### 2. 풀이 도중 새로고침해도 학습 흐름을 잃지 않기

현재 시도 ID와 선택 답안을 탭 세션에 보관하고, 풀이·결과 경로 진입 시 서버의 시도 상태를 다시 조회한다. 이를 통해 같은 브라우저 탭의 새로고침 뒤에도 진행 중 풀이와 제출 결과를 복원한다. 저장된 시도가 없거나 사용자와 맞지 않는 경로는 빈 화면 대신 목록으로 이동한다.

이 선택은 URL만으로 다른 사람의 학습 기록을 공유하지 않는다는 보안·개인화 원칙을 따른다. 장기적인 기기 간 동기화는 별도 제품 요구사항과 서버 API가 필요한 후속 과제다.

### 3. 결과를 끝점이 아닌 다음 학습의 시작점으로 만들기

부분 정답을 단순한 ‘오답’으로만 보이지 않게 맞힌 문항 수를 결과의 주정보로 표시했다. 정답 뒤에는 현재 검색어·언어·등급·유형·북마크 조건 전체에서 아직 풀지 않은 문항을 조회한다. 대상이 소진되면 완료 안내와 목록 복귀를 제공해, 현재 페이지의 문항을 순환하며 반복 제안하는 문제를 막았다.

### 4. 반복 조작과 편집 데이터 손실 줄이기

북마크는 확인창을 거치지 않고 즉시 반영하며 토스트에서 되돌릴 수 있다. 반대로 관리자 편집·수동 등록은 제목, 지문, 권장 시간, 모든 질문·선택지·해설을 비교해 실제 변경이 있을 때만 이탈 확인을 표시한다. 권장 시간은 초 단위 입력 대신 `1분`, `1분 30초`, `2분` 같은 읽기 쉬운 선택지로 바꿨다.

### 5. 키보드로도 끝까지 완료할 수 있게 하기

다이얼로그를 열면 첫 조작 요소로 포커스를 옮기고 Tab 키를 내부에서 순환시킨다. 닫을 때는 실행 버튼으로 포커스를 되돌린다. 답안은 라디오 그룹으로 구현해 방향키와 Home/End 키로 이동·선택할 수 있다.

## AI 협업 방식과 책임 범위

AI 활용은 결과물을 그대로 신뢰하는 방식이 아니라, 다음 반복 과정으로 운영했다.

1. 프로젝트 소유자가 사용자 문제, 완료 기준, 변경 범위를 명시한다.
2. AI 에이전트가 관련 코드를 탐색하고 구현·테스트·문서 초안을 제안한다.
3. 프로젝트 소유자가 동작, 권한 경계, 데이터 손실 가능성, UX 정책을 검토하고 수정 방향을 결정한다.
4. 변경 뒤 타입 검사, 단위·컴포넌트 테스트, 프로덕션 빌드와 문서 정합성을 확인한다.

포트폴리오나 면접에서는 이 저장소에서 실제로 설명·재현할 수 있는 결정만 본인 역할로 소개한다. AI가 개입한 사실을 숨기거나 모든 코드를 수작업으로 작성했다고 주장하지 않는다.

## 검증 근거

- 2026-09-20 기준 `npm test`: 16개 테스트 파일, 24개 테스트 통과
- 같은 기준 `npm run build`: TypeScript 검사와 Vite 프로덕션 빌드 통과
- 회귀 테스트에는 검색 디바운스, 토스트 되돌리기, 권장 시간 선택, 선택지 방향키, 다이얼로그 포커스 순환·복귀, 시도 답안 저장이 포함된다.
- 화면·API·기기별 수동 확인 항목은 [QA 체크리스트](./04-acceptance-checklist.md)에 분리해 관리한다.

초기 화면의 JavaScript 진입 청크는 마지막 로컬 빌드에서 gzip 기준 약 89.8kB였다. 이 값은 라이브러리·번들러 변경에 따라 달라지는 참고 측정치이며, 성능 목표나 운영 지표를 대신하지 않는다.

## 알려진 제한과 다음 검증

- 풀이·결과 복원은 같은 브라우저 탭의 유효한 로그인 세션에 한정된다.
- 실제 Google 로그인, 운영 API, iPhone Safari·Android Chrome의 종단 간 검증은 아직 체크리스트 단계다.
- 백엔드 검사는 PR CI에서 실행하지만, 프런트엔드 테스트는 현재 배포 워크플로에서 빌드만 한다. 프런트엔드 테스트를 PR CI에 추가하는 것이 다음 품질 개선 과제다.
- 사용자 관찰이나 학습 성과에 대한 운영 지표는 아직 수집하지 않았다. 다음 단계에서는 ‘조건에 맞는 미풀이 문항 찾기’, ‘오답 해설 찾기’, ‘장문 미응답 찾기’의 완료 시간과 실패 지점을 측정한다.
